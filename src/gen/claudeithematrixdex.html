Claude I 09:57 UTC

I've read all four branches, and the code has security holes that could expose patients' medical records. I added notes on the code to .claude/CLAUDE.md and committed that locally only; nothing was pushed.

Both repos keep their code on backend and frontend branches. Standard Therapeutics runs the same code as ONITO: identical backend architecture, forked frontend.

Backend (Node/Express + MongoDB)

Accounts and access: users log in and get a 24-hour token that covers both the user and one patient. A patient's users list says who can see them (self, family caring for a dependent, doctors).

Where records live: each patient has one PDF that grows over time. It's stored as <patientId>.pdf in a GitLab repository used as the datastore, reached through GitLab's API. Each upload is merged in front of the existing record with qpdf and committed.

Serving: records are sent with cache headers, so a repeat visit only re-downloads when the file changed.

Sharing: there's a 30-day public share link (/view/:token).

Other: Swagger docs at /docs, deployed on Render, and config.env holds only placeholder values.

Frontend (Angular 20)

Login and sign-up, a profile page for choosing or adding dependent patients, a PDF report viewer with a share link and a browser-side cache, PDF upload, and the public shared-link view.

How the two instances differ

onito-webapp-old: MIT license, ONITO branding. It also has a medicine schedule, a tools page (the rheumatoid-arthritis planner demo, OnCo, EchoNext, HumanGEO, PPBag, STDinfo, Precision AMR, patient similarity search), and "coming soon" notes and patient-info pages.

standard-therapeutics-app: rebranded for standardthera.com under a proprietary license (© 2026), with a "Powered by ONITO" footer. Medicines, tools, notes and patient-info are removed. The main change is that every new patient is automatically shared with a ROOT_USER_ID account, so the clinic sees all patients. That variable is missing from its config.env, so right now nothing valid gets added.

Security problems in both instances

1. Any logged-in user can call GET /api/patient/:id with another patient's ID. The server returns a token for that patient, and that token then downloads their records. Nothing checks that the user is on the patient's users list.

2. Share-link tokens are signed with the same secret as account tokens. If someone with a 30-day view link sends it to POST /api/patient/user, it becomes permanent access to that patient.

3. PUT /api/patient saves whatever the request body contains, so a caller can rewrite the patient's users list and grant themselves or others access.

4. Smaller bugs:

getShareLink returns an empty link when no patient is selected, and it reads an undefined data variable.

/view labels a JSON response as a PDF.

A catch block refers to an err variable that doesn't exist.

The first three matter most. I can draft fixes locally if you want, without pushing anything.
